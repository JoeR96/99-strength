# v2 Phase 6 — Hevy push and pull, server-side Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Hevy the logging source of truth: the server pushes every scheduled session (lifting with Mobility A first, cardio with duration/distance templates) as a Hevy routine with stored ids, pulls completed workouts through the events endpoint on open/refresh/15-minute job, matches them to the plan and completes A2S2 days exactly as manual entry would, and shows unmatched workouts in an inbox.

**Architecture:** A `HevyLink` table maps local keys to Hevy ids (idempotent push). `HevyPullCursor` per user drives `GET /v1/workouts/events?since=`; every pulled workout is stored as a `HevyWorkoutSnapshot` keyed by Hevy workout id (dedupe) and run through `WorkoutMatcher`. Matched lifting workouts become `CompleteDayCommand` calls (AMRAP = last `normal`/`failure` set of the linked exercise); matched cardio/mobility become `TrainingPlan.CompleteSession(..., CompletionSource.Hevy, hevyWorkoutId)`. Unmatched snapshots surface via `GET /hevy/inbox` and `AssignHevyWorkoutCommand`. All Hevy traffic goes through `IHevyClient` (typed, Polly: retry idempotent GETs only, honour `Retry-After`, 15 s timeout, circuit per key).

**Tech Stack:** .NET 10, `A2S.Integration.Hevy` (HttpClientFactory + Polly), EF Core, MediatR, `BackgroundService` for the 15-minute poll, xUnit with recorded JSON fixtures under `tests/A2S.Integration.Hevy.Tests/Fixtures/`.

**Spec:** `docs/v2/brief.md` § 3; Hevy API facts in `docs/v2/audit.md` Appendix B and `docs/v2/plan.md` → Phase 6. Hevy spec (read 8 Nov 2026): header `api-key`; `page`/`pageSize` (max 10); `GET /v1/workouts/events?since=<ISO>&page=&pageSize=` → `{ page, page_count, events: [{ type: "updated", workout: {...} } | { type: "deleted", id, deleted_at }] }` newest first; routines `GET/POST/PUT /v1/routines` (`POST` 201/400/403); `routine_folders`; `exercise_templates` GET/POST with `exercise_type` in `weight_reps, reps_only, bodyweight_reps, bodyweight_assisted_reps, duration, weight_duration, distance_duration, short_distance_weight` and `primary_muscle_group`; sets carry `type` (`warmup|normal|failure|dropset`), `weight_kg`, `reps`, `distance_meters`, `duration_seconds`, `custom_metric`, `rpe` (workouts only); exercises carry `exercise_template_id`, `superset_id`, `rest_seconds`, `notes`; `body_measurements` GET/POST(201/409)/PUT by date with `weight_kg`. No webhooks, no documented rate limit, Pro required.

## Global Constraints

- Keys come only from `IHevyKeyResolver`; never logged, never in fixtures (fixtures use `api-key: test`).
- Every Hevy call is server-side; the browser's `hevyApi` client shrinks to the typed endpoints below.
- Idempotency: push keyed on `localKey`; pull keyed on `hevyWorkoutId`. Re-running any operation changes nothing.
- A2S2 maths untouched: completion goes through `CompleteDayCommand` with the same `ExercisePerformanceRequest` shape the UI sends.
- Local dates via `ILocalClock`; a workout's date is `clock.ToLocalDate(start_time)`.
- Errors map to `Result` with user-facing messages: 401 "Hevy says the key is invalid", 403 "Hevy Pro is required for the API", 429 "Hevy is rate limiting, try again in N s", 5xx/timeouts "Hevy is unavailable, your change is saved locally".

## Review Focus

1. **Same workout event arriving twice** (events replay, two devices): one snapshot, one completion, one habit tick. Pinned in Task 6.5 `PullHevyEventsHandlerTests`.
2. **Workout finished at 23:30Z on 24 Oct 2026** lands on 25 Oct and matches the Saturday session, not Friday's. Pinned in Task 6.4 `WorkoutMatcherTests`.
3. **Routine push retried after a timeout** that actually created the routine: the next push finds the link or title and does not create a duplicate. Pinned in Task 6.3 (`PushRoutine` re-run with a recorded 201 then a timeout).
4. **Deleted event** for a workout already matched: the completion stays (manual undo is the user's call) and the snapshot is flagged `DeletedInHevy`. Pinned in Task 6.5.
5. **Pull with no stored key** does nothing and reports `Skipped` rather than failing the job. Pinned in Task 6.6.

### Task 6.2: `HevyLink` and template catalogue

**Files:** Domain `A2S.Domain/Aggregates/HevySync/HevyLink.cs` (`HevyLinkId`, `UserId`, `HevyLinkKind Routine|Folder|Template|Workout`, `string LocalKey`, `string HevyId`, `DateTimeOffset SyncedAtUtc`), `IHevyLinkRepository` (`FindAsync(UserId, kind, localKey)`, `ListAsync(UserId, kind)`, `Upsert`); Infrastructure config (unique (`UserId`, `Kind`, `LocalKey`)); `HevyTemplateCatalogue` service: resolves a local exercise/drill/protocol to a Hevy template id — library exercises via `ExerciseDefinition.ExternalTemplateId`, mobility drills and cardio protocols via custom templates created once (`POST /exercise_templates`, type `reps_only`/`duration`/`distance_duration`, `primary_muscle_group` from the drill) and remembered as `Template` links with `LocalKey = "drill:<name>"` / `"cardio:<kind>"`.
Tests: catalogue creates a template once and reuses the link; link keys are stable.

### Task 6.3: Push — `PushSessionRoutineCommand`

**Files:** `Application/Commands/Hevy/PushSessionRoutineCommand(Guid PlanId, DateOnly Date, SessionKind Kind, DayNumber? LiftDay)`, handler, `RoutineBuilder` (Application service) producing `HevyRoutineDto`:
- Lifting: title `"{Plan.Name} · W{week} {Label}"` (week = A2S2 week of the linked workout), folder `"{Plan.Name}"`; **Mobility A drills first** (template per drill, sets = drill sets, `reps_only` with reps/seconds/breaths in `notes`), then the day's exercises from `workout.GetPlannedSetsForDay(day)` with `rest_seconds` from `RestDefaults`, `superset_id` for the brief's supersets (paired by `OrderInDay` adjacency flag on the plan session: `SupersetPairs` list of (orderA, orderB)), AMRAP set `type: "failure"`, notes from the existing `BuildExerciseNotes`.
- Cardio: 4×4 → one `duration` template "Norwegian 4×4" with 10 sets (`duration_seconds` per interval, notes "work"/"recovery"); C25K → alternating run/walk sets; LISS → one `distance_duration` set with `duration_seconds`.
- Idempotent: `LocalKey = "plan:{planId}:{date:yyyyMMdd}:{kind}:{liftDay}"`; existing link → `PUT` update instead of `POST`; a `POST` 201 result is linked immediately; a timeout after POST triggers a title lookup before any retry.
- Endpoint: `POST /api/v1/plans/{id}/sessions/push` body `{ date, kind, liftDay }` → `{ routineId, title, created|updated }`; `POST /api/v1/plans/{id}/sessions/push-week?date=` pushes the whole Mon–Sun.
Tests: recorded fixtures for create/update; superset ids; mobility first; review focus 3.

### Task 6.4: `WorkoutMatcher`

**Files:** `Application/Services/WorkoutMatcher.cs`, `MatchResult.cs`.
**Interfaces:** `MatchResult Match(HevyWorkoutSnapshot snapshot, TrainingPlan plan, IReadOnlyList<HevyLink> routineLinks, ILocalClock clock)` → `Matched(ScheduledSession, DateOnly)` | `Unmatched(reason)`; order: (1) `routine_id` → link `LocalKey` → session; (2) same local date + title contains the session label (case-insensitive) ; (3) same local date + single lifting session that day and ≥ 60 % of its exercise template ids present; else Unmatched. Mobility-only workouts (all exercises are drill templates) match a Mobility session or the lift day's warm-up.
Tests: review focus 2; title match; template overlap; a rest-day workout is Unmatched("rest day").

### Task 6.5: Pull — snapshots, cursor, completion

**Files:** Domain `HevyWorkoutSnapshot` (`HevyWorkoutId` PK, `UserId`, `string Title`, `DateTimeOffset StartUtc`, `EndUtc`, `string? RoutineId`, `string RawJson`, `DateOnly LocalDate`, `SnapshotStatus Pending|Matched|Unmatched|Ignored|DeletedInHevy`, `SessionCompletionId?`, `DateTimeOffset UpdatedAtUtc`), `HevyPullCursor(UserId PK, DateTimeOffset LastEventAtUtc, DateTimeOffset LastPulledAtUtc)`; configs; `PullHevyEventsCommand(bool Force)` handler: walks pages until `page_count`, upserts snapshots (never re-completes a `Matched` id), applies `WorkoutMatcher`; a lifting match builds `CompleteDayCommand` performances: for each planned exercise, sets = the workout's `normal|failure` sets for its template id in order, weight kg, reps, `WasAmrap` on the last set when the plan says AMRAP; sends through MediatR (so progression and undo behave exactly as manual); then `plan.CompleteSession(date, Lift, Hevy, liftDay, hevyWorkoutId)`. Cardio/mobility → `CompleteSession` with a `CardioLog` from `duration_seconds`/`distance_meters`. Advances `LastEventAtUtc` to the newest event seen. `Deleted` event → status `DeletedInHevy`.
Endpoint: `POST /api/v1/hevy/pull` → `{ pulled, matched, unmatched, skipped }`.
Tests: review focus 1 and 4; AMRAP mapping against a recorded workout; cursor advances; `CompleteDay` is invoked once per workout.

### Task 6.6: Poll job and inbox

**Files:** `A2S.Api/Jobs/HevyPollService : BackgroundService` — every 15 minutes, for each user with a key and an active plan that has a session today, send `PullHevyEventsCommand`; skips users without a key (review focus 5); logs counts only. `GET /api/v1/hevy/inbox` → unmatched snapshots; `POST /api/v1/hevy/inbox/{hevyWorkoutId}/assign` body `{ date, kind, liftDay? , extra: bool }` → `AssignHevyWorkoutCommand` (completes as in 6.5 or records an `extra` completion); `POST .../ignore`.
Frontend (minimal, Phase 4 PR 6 renders it): `api/hevy.ts` typed client for pull/inbox/assign/push.
Tests: job skips when no key; assign completes and removes from inbox.
